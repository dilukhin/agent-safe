# Явное восстановление через контрольную точку

У некоторых действий нет безопасной обратной команды. Для **универсального
`exec-risky`** можно явно выбрать `--recovery-contract-file` вместо
`--rollback-command` / `--rollback-command-file`. Отсутствие обоих вариантов,
их совместное указание или неверный контракт запрещают выполнение.
Это не разрешение запускать произвольные команды без подготовки.

## Подготовка до действия

1. Указать точную цель, ожидаемые проверяемые свойства, причину и согласование.
2. Проверить существование подходящей контрольной точки и доступность процедуры
   восстановления вне `agent-safe`; получить локальное JSON-свидетельство.
3. Проверить источник свидетельства и его свежесть, вычислить SHA-256 **точных
   байтов** файла и включить его в контракт. Не подставлять фиктивные условия.
4. Передать контракт и отдельную verify-команду. Она должна вернуть JSON
   фактического состояния, подтверждающий непустой набор `assertions`.

Поддерживается только `schema_version: 1`, `kind: "checkpoint"`.
План восстановления (пример структуры, значения необходимо заменить):

```json
{
  "schema_version": 1,
  "kind": "checkpoint",
  "target": "resource:exact-id",
  "checkpoint_id": "checkpoint-001",
  "recovery_source": "backup-system:exact-backup-id",
  "evidence_path": "checkpoint-evidence.json",
  "evidence_sha256": "<64 строчных hex-символа SHA-256 файла>",
  "conditions": {
    "backup_available": true,
    "restore_access_verified": true
  },
  "recovery_steps": [
    "Остановить дальнейшие изменения и прочитать состояние точной цели.",
    "После отдельного согласования восстановить checkpoint-001 штатным средством и проверить результат."
  ]
}
```

Неизвестные или отсутствующие поля контракта запрещены. Идентификаторы и шаги
должны быть непустыми. Названия условий выбираются для конкретной процедуры;
словарь должен быть непустым, все требуемые значения — именно boolean `true`.

Свидетельство, полученное после проверки контрольной точки:

```json
{
  "schema_version": 1,
  "target": "resource:exact-id",
  "checkpoint_id": "checkpoint-001",
  "recovery_source": "backup-system:exact-backup-id",
  "conditions": {
    "backup_available": true,
    "restore_access_verified": true
  },
  "observed_at": "2026-09-18T10:00:00+00:00",
  "valid_until": "2026-09-18T10:30:00+00:00"
}
```

Даты иллюстративные: просроченный пример не запускается. Время включает часовой
пояс; требуется `observed_at <= сейчас < valid_until`. Цель, контрольная точка и
источник должны точно совпадать. Все условия контракта должны подтверждаться
значением `true` в свидетельстве. Дополнительные поля свидетельства допустимы,
но не считаются проверенными и не копируются в журнал.

Оба документа — UTF-8 JSON, не больше 1 МиБ каждый; повторяющиеся ключи и
`NaN`/`Infinity` запрещены. Свидетельство — обычный файл, без `..`, symlink,
junction и reparse point в пути. Относительный `evidence_path` считается от
рабочего каталога действия (`--root` или текущий каталог). Путь самого
`--recovery-contract-file` считается от каталога запуска CLI.

Пример вызова (команды-заглушки нужно заменить согласованными командами):

```bash
safe exec-risky \
  --channel local --domain system \
  --target "resource:exact-id" --reason "согласованное изменение" \
  --expected-state-file expected.json \
  --recovery-contract-file recovery.json \
  --verify-command-file verify-command.txt \
  --approved -- exact-program exact-argument
```

Критические команды по-прежнему требуют `--allow-critical`. Новый режим не
меняет deny-права OpenCode и не добавляет новые виды разрешённых действий.

## Журнал и остановка при неопределённом результате

До основной команды записываются `planned`, точная команда, цель, expected state,
контракт, проверенные поля свидетельства и его хеш. Запись сбрасывается через
`fsync`; затем создаётся эксклюзивный временный `INCIDENT_BLOCKED`, также с
`fsync`. Если фиксация не удалась, команда не запускается.

После выполнения добавляется итоговая запись с тем же `txn_id`. При успехе
она сбрасывается до снятия собственного временного барьера. `Journal.find`
возвращает последнюю полную запись, а не первоначальный план или запись события.
Старые записи и режим `rollback-command` не требуют миграции.
`safe recovery-plan` при наличии блокировки выбирает её транзакцию, включая
незавершённый `planned`, и показывает контракт без исполнения шагов.

Ошибка команды, timeout, прерывание, ошибка verify, несовпадение assertions
или ошибка receipt оставляют `unexpected` и блокировку. Жёсткое завершение
процесса может оставить только `planned` и временную блокировку: это **не успех**,
нужны диагностика и отдельное согласование восстановления. Нового запуска,
слепого повтора или автоматического отката нет. Receipt запускается только
после успешной проверки результата.

`metadata.recovery.mode` различает `rollback-command` и `checkpoint`.
Для checkpoint `undo` — `manual-recovery`, `redo` — `manual-review-required`;
`undo`/`redo` CLI отказываются выполнять такие записи. Шаги восстановления —
инструкция для согласованной ручной или специализированной процедуры, не shell.

## Границы гарантии

SHA-256 подтверждает соответствие файлу, одобренному в контракте, **не подлинность
источника и не фактическую восстанавливаемость backup**. `agent-safe` проверяет
локальное свидетельство, но сам не опрашивает внешнюю систему и не создаёт backup.
Подготовку свидетельства и проверку возможности восстановления выполняет
доверенный оператор или специализированный адаптер. Не включайте секреты в
контракт: его поля сохраняются в журнале.

Рабочий каталог и `.agent-safety` должны быть доверенными; операции в одном
корне выполняются последовательно. Это не защита от конкурентного злоумышленника,
не распределённая блокировка и не гарантия переживания любой аварии хранилища.
Контракт не копирует backup и не делает архив восстановления самодостаточным
(отдельная задача #15). `system-change`, `yc-change` и `ssh-relay-risky` пока
сохраняют обязательную rollback-команду. Реальные SSH/cloud/VM-изменения для
проверки этой реализации не требуются и тестами не выполняются.
