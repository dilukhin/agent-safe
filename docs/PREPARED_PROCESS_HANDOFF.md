## Реализованная независимая часть

Первый внутренний потребитель — recover и его отдельная проверка. Исполнитель _run,
журнал, собственная recovery-транзакция, ACTIVE и сохранение исходного INCIDENT_BLOCKED
остаются прежними. Нет нового публичного запуска spec или флага обхода разрешения.

core.rollback.prepare_process выдаёт frozen PreparedProcess только после load_bundle
и раскрытия artifact-ссылок. Вложенные сведения — frozen dataclass и tuple, без
изменяемых словарей/массивов. Это внутренний Python API, не формат разрешения:

| Сведения | Источник и смысл |
| --- | --- |
| source_txn_id, attempt_txn_id, role | Исходная и новая recovery-транзакции; роли process (восстановление) и verify различны |
| program, argv, cwd | Проверенный Python, точные аргументы без program, абсолютный каталог; artifact уже заменён путём сохранённой копии |
| timeout_seconds, stdin_utf8 | Целое 1–3600; None означает DEVNULL, пустая строка — пустой PIPE |
| program_identity, cwd_identity | Проверенные локальные stat-сведения по правилам профиля |
| artifacts | ID, путь сохранённой копии, размер, SHA-256 и локальная stat-идентичность каждого сохранённого файла |
| manifest_sha256 | SHA-256 разобранного и канонически сериализованного manifest; не operation_identity и не grant |

Оба снимка готовятся до начала восстановления. Непосредственно перед каждым _run
revalidate_process заново проверяет комплект и сравнивает свежие факты с исходным
снимком, включая роль и транзакции. Свежие данные не заменяют исходные argv/stdin.
Изменение приводит к остановке и необходимости нового рассмотрения. Исполнитель
получает аргументы именно исходного снимка. Даже замена сохранённого файла теми же
байтами после подготовки обнаруживается по stat-идентичности.

Одинаковые program/argv сами по себе не связывают вызовы разных ролей или попыток.
Указанные ID — сведения корреляции, не неподделываемое доказательство.
PreparedProcess нельзя принимать от недоверенного caller как подтверждённые facts.
Frozen Python-объект не является границей безопасности против произвольного кода
в том же процессе. Полное устранение гонки между проверкой пути и spawn не заявляется.

Структурированный _run кодирует stdin в UTF-8 до spawn и передаёт bytes через
бинарный канал. LF и CRLF не преобразуются; stdout/stderr строго декодируются из UTF-8.
Неизвестный исход, включая потерю декодируемого результата после spawn, не повторяется.
Legacy text-вход остаётся совместимым. Все неизвестные поля ProcessSpec и неподдержанные
env_dependencies отвергаются; наследуемое окружение не считается герметичным.

## Недостающий интерфейс opencode_permissions #34

До интеграционного PR нужно опубликовать один согласованный контракт следующих операций,
переиспользующий NormalizedOperation и существующее решение политики:

1. **Доверенная проекция/acquisition.** Указать модуль, вызываемый API и версию локального
   профиля, принимающего эти проверенные facts. В execution.argv добавить program ровно
   один раз. Явно связать stdin mode/точные байты, timeout, пути/содержимое/идентичность
   сохранённых зависимостей. Неподдержанные поля, секреты и неизвестные effects — non-ALLOW;
   нельзя молча потерять их при формировании пустого context_dependencies.
2. **Представление файловых идентификаторов.** Зафиксировать версию и точную lossless
   кодировку object_identity, а также profile-specific descriptors dependencies.
   Внутренние stat tuple содержат большие Python int, в том числе наносекунды: их
   запрещено напрямую передавать JSON-числами в op-jcs-v1. Десятичные строки с именами
   компонентов — возможный вариант для утверждения в #34, пока не новый формат agent-safe.
   Не округлять, не использовать repr и не менять canonicalizer ради timestamps.
3. **Выдача решения и связывание вызова.** Определить владельца аутентичного continuation,
   его транспорт, привязку к operation_identity, session/call, source/attempt и роли,
   сроки действия, отказ/ASK и правила одноразового использования. agent-safe предоставляет
   локальные ID попытки/роли; владелец authority и защиты от replay — opencode_permissions.
4. **Проверка и потребление решения перед spawn.** Опубликовать вызываемый API и ошибки
   проверки подлинности/срока/привязки/replay, порядок проверки и одноразового потребления
   при not_started/unknown. agent-safe повторно проверяет исходный снимок и runtime
   preconditions; при drift старое решение недействительно, требуется новый запрос.
   Скрытая пересборка команды или автоматический повтор запрещены.

Разрешение основной mutation не наследуется восстановлением или его verify. Для них
нужны отдельные bindings и проверки перед соответствующим spawn. До запуска verify
решение должно относиться к его точному снимку и роли, даже если восстановление прошло.
Нужно также явно определить охват подготовительных служебных записей: комплект,
журнал и барьеры остаются ответственностью agent-safe и не прячутся внутри разрешения
на единственный дочерний процесс.

Пока этого контракта нет, интеграция управляемого разрешения **не реализована**.
В существующем ручном CLI --approved подтверждает отдельное ручное согласование,
но не является решением opencode_permissions. Нового managed-пути с заглушкой ALLOW,
самодельного токена или callback, объявляющего операцию разрешённой, здесь нет.
SHA-256 Python-скрипта подтверждает содержимое, но не безопасность его действий.

## Проверки и следующий отдельный объём

Runtime fixtures читают stdin дочерним Python через buffer и сравнивают hex байтов:
LF, CRLF, смешанные переводы строк, Unicode, пустой PIPE и DEVNULL. Тип дескриптора и EOF
проверяются внутри ребёнка. Матрица — Windows/Ubuntu × Python 3.10/3.14.
Проверяется отказ до _run при подмене argv/stdin/timeout/роли/ID, сохранённого файла,
cwd и наблюдаемых executable metadata. Существуют проверки отдельного verify,
сохранения блокировки, сбоев журнала и запрета повтора после unknown.

Это ещё **не** интеграционные тесты разрешений. Чужое/истёкшее решение, повторное
использование continuation, сохранение native DENY/ASK и точная проекция identity
должны проверяться на опубликованном API #34; успешных проверок несуществующего API
не заявляем. Публичные verify/receipt/main-spec флаги #25A — следующий отдельный PR
с совместимостью legacy. Внутренняя готовность восстановления не закрывает #25A или #34.
