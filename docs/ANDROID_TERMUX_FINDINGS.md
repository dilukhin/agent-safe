# Findings: agent-safe при работе с ADB и Termux

Дата наблюдения: 2026-07-23.

## Контекст

Практическая сессия включала:

- создание SSH-ключа в Termux через ADB без root;
- изменение `authorized_keys` на трёх удалённых VPS;
- замену конфигурации `tunnelctl` внутри приватного каталога Termux;
- многократную очистку созданных локальных и Android-временных файлов.

Высокорисковые изменения SSH и рабочей конфигурации выполнялись с `expected_state`, rollback и verify. Для временных файлов применялся тот же протокол, что выявило ограничения текущей модели риска.

## Подтверждённые наблюдения

### 1. Лексическая классификация переоценивает точное удаление временных файлов

`safe exec-risky` классифицировал как `critical` точное удаление нескольких известных файлов из `/sdcard/Download` из-за наличия `rm` и `-f`. При этом одновременно выполнялись следующие условия:

- список путей был явным, без wildcard и рекурсии;
- все файлы были созданы текущей сессией;
- файлы находились в известном временном контуре;
- до удаления была создана локальная резервная копия;
- SHA-256 локальной и удалённой копий совпадали;
- существовали исполнимые rollback и post-action verify.

Первый отказ без rollback был полезен. Повторное требование `--allow-critical` после подтверждённого backup и verify почти не добавило защиты.

### 2. Нет пакетной транзакции для набора файлов

`safe fs-trash` принимает один путь. Когда временные файлы лежат непосредственно в общем каталоге, каждый из них требует отдельной транзакции. В сессии это породило десятки receipt, большой вывод и дополнительные точки отказа.

Нельзя решать проблему обходом `safe` через `Remove-Item`, `rm` или цикл shell. Нужна штатная пакетная операция.

### 3. Expected state может обещать больше, чем проверяет verify

Один expected state включал утверждения о сохранности SSH-ключа и рабочей конфигурации, тогда как verify проверял только отсутствие временных файлов. Транзакция завершилась успешно, хотя не все заявленные свойства были проверены напрямую.

Это создаёт риск ложной полноты: успешный verify воспринимается как доказательство всего JSON expected state.

### 4. Generic adapter не понимает семантику ADB UI

Из-за Android sandbox команда в Termux запускалась через:

1. `adb shell input text` для ввода короткой команды;
2. `adb shell input keyevent KEYCODE_ENTER` для выполнения.

`safe` видел только нажатие Enter и оценивал его как неизвестное state-changing действие. Фактическая операция находилась в заранее переданном shell-скрипте и не была доступна классификатору.

Следствия:

- target и receipt описывают реальную цель только со слов вызывающего кода;
- redo в виде повторного Enter семантически некорректен;
- rollback зависит от фокуса Termux и доступности локальных вспомогательных файлов;
- нельзя доказать, что введённая строка не была обрезана или отправлена в другое окно.

### 5. Rollback может перестать быть самодостаточным после cleanup

Некоторые rollback-команды ссылались на `.ps1` и backup-файлы в локальном temp. После успешной проверки эти файлы были перемещены в safety-trash. Старый receipt сохранил текст команды, но прямой rollback перестал работать без предварительного восстановления его зависимостей.

### 6. Safety-trash очищает рабочий каталог, но сохраняет данные

`safe fs-trash` корректно убирает файл из исходного места и даёт undo, однако это не окончательное удаление. Диагностические данные остаются в `~/.agent-safety/trash`. Нужны явные правила retention и контролируемая garbage collection.

## Что сработало правильно

- удаление без rollback было остановлено до изменения состояния;
- неожиданный timeout длинного `adb input text` привёл к Recovery Mode, а не к слепому повтору;
- изменение production `authorized_keys` выполнялось отдельно для каждого хоста с точным rollback и проверкой владельца/режима;
- конфигурация Termux заменялась скриптом с автоматическим восстановлением при ошибке `doctor`;
- Android-файлы удалялись только после проверки backup по SHA-256.

Строгий протокол необходимо сохранить для ключей, production-доступа, конфигурации, неизвестных путей и действий с большим blast radius.

## Рекомендуемые доработки

### P0. Связать expected state и verify

Варианты реализации:

- expected state задаётся набором именованных проверок;
- verify возвращает JSON с теми же ключами;
- транзакция завершается только при полном совпадении;
- неподтверждённые поля явно помечаются как декларативные и не участвуют в результате проверки.

Критерий приёмки: успешная транзакция не может утверждать `resource_preserved=true`, если verify не вернул это свойство.

### P0. Добавить пакетный `fs-trash`

Предлагаемый интерфейс:

```text
safe fs-trash-batch --manifest files.json --reason "..."
```

Требования:

- одна транзакция и один каталог trash;
- точная проверка всех путей до изменения;
- запрет symlink/reparse-point escape;
- запрет выхода за разрешённые корни;
- rollback всего набора;
- итоговая проверка отсутствия всех исходников;
- manifest сохраняется в receipt.

### P1. Контекстная оценка временных путей

Удаление можно понижать до `cautious` или `high`, но не `critical`, если одновременно выполнены условия:

- корень создан текущей транзакцией или находится в явно разрешённом temp-контуре;
- удаляется точный файл либо целиком выделенный каталог задачи;
- отсутствуют wildcard, symlink и выход через `..`;
- путь не содержит ключи, конфигурацию, Git-метаданные или пользовательские документы;
- существует проверяемый rollback либо данные объявлены воспроизводимыми.

`rm -rf`, неизвестный путь и удаление production-конфига должны оставаться `critical`.

### P1. Специализированный ADB/Termux adapter

Предлагаемые операции:

```text
safe adb-push
safe adb-trash
safe adb-termux-run
```

Adapter должен фиксировать:

- serial устройства;
- ожидаемый foreground package;
- локальный и удалённый SHA-256 скрипта;
- точную команду внутри скрипта, а не только `KEYCODE_ENTER`;
- result-marker и post-state;
- самодостаточный rollback.

Перед Enter adapter должен повторно проверять foreground window. Длинный inline-ввод должен быть запрещён или ограничен безопасной длиной.

### P1. Жизненный цикл rollback

Rollback-артефакты следует копировать в каталог самой транзакции. После финализации возможны состояния:

- `active`: автоматический rollback доступен;
- `finalized`: пользователь подтвердил удаление rollback-данных;
- `expired`: retention истёк, rollback больше не гарантируется.

### P2. Retention и garbage collection

Нужна команда предварительного просмотра и очистки safety-trash по TTL, например:

```text
safe trash-preview --older-than 30d
safe trash-purge --manifest preview.json --approved
```

Очистка должна быть отдельной критической транзакцией, а не скрытым фоновым удалением.

## Улучшение рабочего процесса без изменения кода

До реализации backlog следует с начала задачи создавать выделенные каталоги:

```text
<temp>/opencode/<task-id>/
/sdcard/Download/opencode/<task-id>/
```

Тогда все артефакты можно проверить и удалить одной транзакцией вместо удаления каждого файла отдельно.

## Итог

Проблема не в самой осторожности, а в недостатке контекста и пакетных операций. Ослаблять универсальный протокол нельзя. Следует уменьшить число транзакций, сделать verify структурным и добавить адаптер, который понимает фактическую ADB/Termux-команду.
