## Подтверждённые замечания

### P1 — файловые undo/redo (#26)

`_do_move` проверяет exists и наличие родителя, затем вызывает shutil.move. Общий preflight прямых операций, сверка исходного объекта, блокировка обычного redo и проверка результата в этом пути отсутствуют. `cmd_undo/cmd_redo` дополнительных проверок не добавляют.

| Воспроизведение | Наблюдаемый результат |
| --- | --- |
| После fs-move исходный родитель переименован и заменён symlink на другой временный каталог; публичный CLI undo | exit=0, файл перемещён через ссылку, событие undo, blocked=false |
| move → undo; затем блокировка другого инцидента; публичный CLI redo | exit=0, новое перемещение выполнено, старая блокировка остаётся |
| Исходный перемещённый объект сохранён в стороне; по его прежнему адресу создан другой файл | undo возвращает посторонний файл и записывает успех |
| Подмена shutil.move: перемещение выполнено, затем OSError | Файл перемещён; запись восстановления и новая блокировка отсутствуют |
| Подмена shutil.move: возврат без перемещения | Объект остаётся на прежнем месте, но журнал пишет undone |

Первые три случая — реальные локальные файловые операции. Последние два — имитация ошибок, которая доказывает отсутствие обработки, но не частоту таких сбоев в эксплуатации. Ссылочная подмена выполняется до undo и не требует узкой гонки. Windows-поведение не заявляется проверенным этим воспроизведением.

Источник: [fs.py](../../src/agent_safe/adapters/fs.py), [journal.py](../../src/agent_safe/core/journal.py). [#26](https://github.com/dilukhin/agent-safe/issues/26) содержит воспроизводимый пример и критерии отдельного исправления. Приоритет — до пакетного восстановления #14.

### P1 — SSH verify принимает другой endpoint (#27)

Использованы существующие `risky_payload/verify_payload` и подмена `_run_machine`; реальная сеть не использовалась. Успешное основное действие сообщало session=prod, host=198.51.100.10, port=22, user=operator. При verify независимо изменялось одно поле:

| Изменённое поле verify | Результат |
| --- | --- |
| remote_host=198.51.100.99 | done, verification_complete=true, blocked=false |
| remote_port=2222 | done, verification_complete=true, blocked=false |
| remote_user=other-user | done, verification_complete=true, blocked=false |

`_parse_machine_payload` и `ssh_relay_risky` не проверяют эту связность. Подтверждено принятие противоречивого ответа; изменение привязки живой сессии между вызовами не воспроизводилось. [#27](https://github.com/dilukhin/agent-safe/issues/27) отделяет исправление контракта от последующего реального прогона.

Совпадение endpoint между двумя ответами ещё не доказывает, что первое действие выполнено на заранее разрешённой машине. Человеческий host_label не является такой гарантией; эта граница включена в план интеграционного прогона.

Проход штатного набора не опровергает новые замечания: перечисленные случаи им не покрываются. Данные относятся к проверенной базе; CI документационного PR учитывается отдельно по его head. Новый runtime в этом аудите не создавался.
