# План доработок agent-safe по результатам испытаний ADB и Termux

Дата составления: 2026-07-26.

Исходный документ: [`ANDROID_TERMUX_FINDINGS.md`](ANDROID_TERMUX_FINDINGS.md).

## 1. Цель

Устранить выявленные при практической работе с ADB и Termux недостатки, не ослабляя универсальную safety-модель:

- связать `expected_state` с фактическим результатом `verify`;
- исключить опасное разыменование symlink и Windows reparse point;
- добавить пакетное обратимое перемещение набора файлов в safety-trash;
- сделать rollback самодостаточным и явно управлять его жизненным циклом;
- определить безопасное окончательное удаление устаревших данных;
- учитывать подтверждённый контекст временных файлов без ослабления generic-классификатора;
- добавить специализированный ADB/Termux adapter.

Проект остаётся CLI-инструментом на Python stdlib. Архитектуру без необходимости не переписывать, сторонние зависимости не добавлять.

## 2. Порядок выполнения

Работу разделить на независимые логические changeset. Каждый этап реализовывать в отдельной ветке и отдельном PR. Не объединять структурную верификацию, файловые операции, retention и ADB adapter в один большой PR.

Рекомендуемая последовательность:

1. принять findings в `master`;
2. структурная верификация `expected_state`;
3. защита путей от symlink/reparse point;
4. пакетный `fs-trash`;
5. жизненный цикл rollback;
6. retention и окончательная очистка;
7. контекстная оценка временных файлов;
8. ADB/Termux adapter.

## 4. Этап 1 — P0: структурная верификация expected state

### 4.1. Проблема

Текущий `exec_risky()` сохраняет `expected_state`, но определяет успех только по кодам возврата основной, проверочной и receipt-команд. Вывод `verify` не сопоставляется с ожидаемым состоянием. Команда проверки может вернуть `0`, проверить только часть свойств или вывести произвольный текст, после чего транзакция всё равно получает `done`.

### 4.2. Контракт

Ввести различие между проверяемыми утверждениями и декларативным контекстом:

```json
{
  "assertions": {
    "temporary_files_absent": true,
    "ssh_key_preserved": true
  },
  "declarations": {
    "operation": "cleanup"
  }
}
```

Проверочная команда возвращает JSON-объект фактического состояния:

```json
{
  "temporary_files_absent": true,
  "ssh_key_preserved": true,
  "diagnostics": {}
}
```

Правила:

- все поля `assertions` обязательны в результате проверки;
- типы и значения должны совпадать;
- дополнительные поля фактического состояния допустимы;
- отсутствующее поле, неверный тип, несовпадение или невалидный JSON дают `unexpected`;
- `declarations` сохраняются в журнале, но не считаются проверенными;
- receipt выполняется только после полного совпадения assertions;
- risky-действие с непустыми assertions требует `verify`;
- успешная транзакция не может утверждать свойство, которого нет в фактическом результате проверки.

### 4.3. Реализация

Добавить модуль:

```text
src/agent_safe/core/verification.py
```

Предусмотреть функции:

- разбор и валидация expected state;
- разбор JSON из stdout verify-команды;
- рекурсивное либо явно ограниченное сравнение assertions;
- формирование списка совпавших, отсутствующих и несовпавших полей;
- безопасное представление ошибок без утечки секретов.

Обновить:

- `src/agent_safe/core/models.py`;
- `src/agent_safe/adapters/exec_adapter.py`;
- `src/agent_safe/adapters/system.py`;
- `src/agent_safe/adapters/yc.py`;
- `src/agent_safe/adapters/ssh_relay.py`;
- `src/agent_safe/cli.py`;
- README, `docs/ADAPTERS.md` и OpenCode skills с примерами risky-команд.

Проверку реализовать централизованно в generic adapter. Тонкие адаптеры `system`, `yc` и `ssh_relay` не должны дублировать алгоритм сравнения.

### 4.4. Журнал

Зафиксировать в записи транзакции как минимум:

```json
{
  "verification_complete": true,
  "verified_assertions": {},
  "missing_assertions": {},
  "mismatched_assertions": {},
  "actual_state": {}
}
```

Не менять старые записи журнала и обеспечить их чтение.

### 4.5. Тесты

Обязательные сценарии:

- verify вернул `0`, JSON полностью совпал — `done`;
- verify вернул `0`, но отсутствует поле — `unexpected` и recovery lock;
- verify вернул `0`, но значение отличается — `unexpected`;
- verify вернул невалидный JSON — `unexpected`;
- verify завершился ненулевым кодом — `unexpected`;
- дополнительные поля actual state не мешают успеху;
- receipt не запускается при любом несовпадении;
- декларативные поля не помечаются как проверенные;
- существующие read-only и файловые операции не регрессируют.

Изменение контракта допускает повышение версии до `0.4.0`.

## 5. Этап 2 — P0: защита файловых путей

### 5.1. Проблема

`fs_move()` и `fs_trash()` используют `Path.resolve()`. При передаче symlink операция может работать с фактической целью ссылки, а не с самой ссылкой. На Windows отдельно учитывать junction и другие reparse point.

### 5.2. Реализация

Добавить общий файловый preflight без следования по ссылкам:

- использовать `lstat` до канонизации;
- определять symlink;
- на Windows определять reparse point/junction средствами stdlib;
- по умолчанию отклонять ссылки и reparse point;
- проверять разрешённый корень;
- запрещать выход через `..`;
- проверять пересечение source и destination;
- фиксировать идентичность объекта до действия и повторно проверять её непосредственно перед move;
- проверять родительские каталоги;
- не снижать риск для `.git`, ключей, конфигурации и пользовательских документов.

Не вводить платформозависимые обязательные зависимости. Platform-specific код изолировать в небольших вспомогательных функциях.

### 5.3. Критерии приёмки

- `fs-trash` не перемещает цель symlink;
- после отказа ссылка и её цель остаются без изменений;
- Windows junction/reparse point отклоняется;
- обычные файлы и каталоги работают как раньше;
- `fs_move` и `fs_trash` используют единые проверки;
- ошибка preflight не создаёт успешную транзакцию;
- проверки работают на Windows, Linux, macOS и Termux настолько, насколько это поддерживает stdlib.

## 6. Этап 3 — P1: пакетный fs-trash

### 6.1. Интерфейс

Предпочтителен двухшаговый интерфейс:

```text
safe fs-trash-preview path1 path2 path3 --output trash-manifest.json
safe fs-trash-batch --manifest trash-manifest.json --reason "..." --approved
```

Preview является read-only. Batch выполняет одно логическое изменение.

### 6.2. Manifest

Для каждого объекта сохранять:

```json
{
  "path": "/exact/path",
  "type": "file",
  "size": 1234,
  "sha256": "...",
  "identity": {},
  "allowed_root": "/exact/root"
}
```

Manifest также содержит:

- версию формата;
- время создания;
- хеш всего manifest;
- список разрешённых корней;
- число объектов;
- суммарный размер;
- сведения, достаточные для повторного preflight.

### 6.3. Выполнение

Алгоритм:

1. проверить весь manifest до первого изменения;
2. отклонить дубликаты и пересекающиеся цели;
3. отклонить одновременное указание каталога и вложенного объекта;
4. отклонить symlink/reparse point;
5. отклонить объекты, изменившиеся после preview;
6. создать один каталог `.agent-safety/trash/<txn-id>/`;
7. переместить объекты по одному с журналированием промежуточного состояния;
8. при ошибке остановиться и попытаться вернуть уже перемещённые объекты;
9. даже после успешного автоматического возврата считать промежуточную ошибку инцидентом;
10. проверить отсутствие всех исходников и наличие всех объектов в trash.

Это транзакционное поведение runtime, но не следует называть его атомарностью файловой системы.

### 6.4. Undo

Undo набора должен предварительно проверить:

- наличие всех объектов в trash;
- отсутствие исходных путей;
- неизменность manifest и хешей;
- наличие родительских каталогов.

Если предусловия нарушены, не начинать частичное восстановление и перейти к recovery plan.

### 6.5. Критерии приёмки

- один набор — одна транзакция и одна основная journal-запись;
- один каталог trash;
- manifest сохраняется в evidence транзакции;
- preflight-ошибка не перемещает ничего;
- частичная ошибка запускает rollback уже перемещённых объектов;
- verify охватывает весь набор;
- undo восстанавливает весь набор либо не начинает действие;
- redo не использует неоднозначные пути и повторно проверяет предусловия.

## 7. Этап 4 — P1: жизненный цикл rollback

### 7.1. Проблема

Generic risky action хранит rollback-команду как текст, который может ссылаться на временные скрипты или backup-файлы. После cleanup эти зависимости могут исчезнуть. Кроме того, общий `undo` поддерживает только встроенные операции перемещения и не должен молча исполнять произвольный shell-текст.

### 7.2. Структура транзакции

Добавить каталог:

```text
.agent-safety/transactions/<txn-id>/
  transaction.json
  expected-state.json
  actual-state.json
  rollback/
  evidence/
  manifest.json
```

Rollback-скрипты и необходимые backup-файлы копировать внутрь транзакции до основного действия. Сохранять SHA-256, размер, тип и назначение каждого артефакта.

### 7.3. Состояния

Использовать явные состояния:

```text
active
finalized
expired
unavailable
```

`expired` означает окончание гарантированного срока хранения, но само по себе не удаляет данные.

### 7.4. Команды

Предлагаемый интерфейс:

```text
safe rollback-plan <txn-id>
safe rollback-apply <txn-id> --approved
safe rollback-finalize <txn-id> --approved
```

`rollback-apply`:

- разрешён в Recovery Mode;
- выполняет только заранее зафиксированную rollback-команду;
- проверяет хеши и наличие всех зависимостей;
- имеет отдельный expected state восстановления и verify;
- создаёт отдельную recovery-транзакцию;
- не снимает recovery lock автоматически.

`undo` оставить только для встроенных структурированных операций, таких как `fs-move`, `fs-trash` и их пакетный вариант.

### 7.5. Критерии приёмки

- cleanup не удаляет артефакт активного rollback;
- повреждённый или отсутствующий rollback-файл блокирует исполнение до изменения состояния;
- rollback после завершения исходной задачи остаётся воспроизводимым;
- finalize требует явного подтверждения;
- recovery lock снимается только отдельной командой после ручного анализа;
- старые записи журнала продолжают читаться.

## 8. Этап 5 — P2: retention и окончательная очистка

### 8.1. Интерфейс

```text
safe trash-preview --older-than 30d --output purge-manifest.json
safe trash-purge --manifest purge-manifest.json --approved
```

### 8.2. Политика

`trash-purge` является критической и необратимой операцией. Она:

- не выполняется при активном Recovery Mode;
- не удаляет данные активных rollback-транзакций;
- повторно проверяет manifest перед удалением;
- отказывается при изменении состава, identity или хешей;
- записывает точный перечень окончательно удалённых объектов;
- не выполняется автоматически или в фоне;
- не маскируется под обратимое удаление.

Отдельно определить retention для:

- trash;
- snapshots;
- command-output;
- evidence;
- recovery;
- finalized rollback-артефактов.

По умолчанию ничего не удалять без явного purge.

## 9. Этап 6 — P2: контекстная оценка временных файлов

Generic-классификатор команд не ослаблять: неизвестный `rm`, `remove` или `delete` остаётся критическим.

Понижение риска допускается только внутри специализированного файлового адаптера после структурного preflight при одновременном выполнении условий:

- точные пути;
- явно разрешённый корень;
- отсутствуют wildcard и `..`;
- отсутствуют symlink/reparse point;
- объект создан текущей задачей либо находится в workspace, созданном `safe`;
- объект не является ключом, конфигурацией, Git-метаданными или пользовательским документом;
- существует проверенный rollback либо объект явно объявлен воспроизводимым;
- blast radius ограничен manifest.

Рассмотреть команду:

```text
safe temp-workspace --task-id <id>
```

Она создаёт выделенный каталог и записывает provenance в журнал. Удаление содержимого такого workspace может оцениваться как `cautious` или `high`, но не становится read-only.

## 10. Этап 7 — P2: ADB/Termux adapter

### 10.1. Команды

```text
safe adb-push
safe adb-trash
safe adb-termux-run
```

### 10.2. Инварианты adb-termux-run

Adapter фиксирует:

- точный serial устройства;
- ожидаемый foreground package;
- локальный и Android-путь скрипта;
- локальный и удалённый SHA-256;
- точную команду внутри скрипта;
- короткую фиксированную команду запуска;
- уникальный result-marker;
- timeout;
- фактическое post-state;
- самодостаточный rollback.

Перед `KEYCODE_ENTER` повторно проверяется foreground package.

Запретить:

- длинный inline-ввод через `adb shell input text`;
- redo как повторное нажатие Enter;
- выполнение без проверки serial;
- выполнение при неожиданном foreground window;
- продолжение после timeout;
- reliance только на состояние Android UI;
- rollback, зависящий от внешнего временного файла.

### 10.3. Тестирование

Основные тесты строить через подмену subprocess и детерминированные fixtures. Отдельно подготовить ручной интеграционный сценарий:

1. push скрипта;
2. совпадение SHA-256;
3. запуск при правильном foreground package;
4. получение result-marker;
5. неверное foreground window;
6. обрезанный ввод;
7. timeout и Recovery Mode;
8. отсутствующий rollback-файл;
9. пакетное удаление Android-временных файлов;
10. проверка восстановления после unexpected result.

## 12. Общие проверки

После каждого кодового этапа:

```bash
PYTHONPATH=src python -m unittest discover -s tests -v
PYTHONPATH=src python -m agent_safe --help
PYTHONPATH=src python -m agent_safe opencode-bootstrap --scope project --dry-run
```

Если менялись bootstrap, templates или OpenCode skills, дополнительно проверить два последовательных запуска `--apply`: второй запуск должен быть no-op и не добавлять новую journal-запись.

Для файловых операций тесты должны использовать временные каталоги и не затрагивать реальные пользовательские данные.

Если проверки не запускались или были невозможны, это явно указывать в PR.

## 13. Общие ограничения реализации

- источник истины — фактическое содержимое файлов и результаты тестов;
- сначала изучать текущую реализацию;
- не делать массового косметического рефакторинга;
- не ослаблять deny-политику OpenCode;
- не выводить секреты в stdout, stderr, journal и evidence;
- unknown command + external state остаётся high risk;
- unexpected result после risky action всегда переводит систему в Recovery Mode;
- изменения должны работать на Windows, Linux, macOS и Android/Termux;
- использовать только Python stdlib;
- документация, сообщения, логи и комментарии — на русском там, где это относится к проекту.
