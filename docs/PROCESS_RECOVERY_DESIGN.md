## Решение и границы

Расширить существующий исполнитель общим небольшим представлением процесса `ProcessSpec`. Не добавлять отдельный универсальный `safe run-spec`, новую модель разрешений или автоматический запуск rollback. Для #15 сначала реализовать минимальный внутренний потребитель этого представления; остальные публичные входы — отдельный PR #25A.

Первый объём #15: локальный `exec-risky`, обычные локальные несекретные файлы зависимостей и отдельное явно вызываемое восстановление. Проверка checkpoint из #23 остаётся самостоятельным режимом. Адаптеры SSH/YC/system не получают новые возможности автоматически. Необъявленные зависимости, внешние backup и удалённые скрипты не становятся воспроизводимыми из-за сохранения локального файла.

Существующая основная команда уже выполняется как `list[str]`; хрупкость находится в `_split_shell_command` для verify/receipt и хранении rollback как текста. Сам rollback сейчас не исполняется общим undo. Поэтому задача — уточнить вход и восстановление, сохранив один исполнитель и `ActionRecord`/`Journal`.

## Предлагаемый ProcessSpec v1

Один UTF-8 JSON-объект. Неизвестные поля/версия, повтор ключа, NUL, некорректный Unicode, NaN/Infinity, неверные типы — отказ до запуска. `argv` не включает program и сохраняет порядок, пустые строки и точное содержимое.

| Поле | Правило первого варианта |
| --- | --- |
| schema_version | Целое 1; bool не допускается |
| program | Непустой абсолютный путь к исполняемому файлу, проверенный до spawn; не поиск по PATH |
| argv | Массив строк; никакой обратной сборки в shell text |
| cwd | Абсолютный существующий каталог; не скрытое наследование каталога запуска |
| shell | Только false |
| timeout_seconds | Целое 1–3600, не bool |
| stdin_utf8 | Необязательная строка до 64 КиБ; отсутствие означает DEVNULL, пустая строка — пустой PIPE; точные UTF-8 байты без преобразования LF/CRLF |
| env_dependencies | Необязательный список имён. Это предложение зависимостей для доверенного профиля, не разрешение произвольных env overrides |

Предлагаемые ограничения входа: объект до 1 МиБ, максимум 1024 аргумента, каждая строка аргумента до 32 КиБ в UTF-8. Это верхние границы валидации, не обещание поддержки такой длины ОС; ошибка запуска обрабатывается явно. Конкретные значения подтвердить при согласовании.

Пример структуры, не готовая команда для запуска:

```json
{
  "schema_version": 1,
  "program": "/usr/bin/python3",
  "argv": ["-I", "/approved/helpers/check_state.py", "--target", "/approved/test/item"],
  "cwd": "/approved/test",
  "shell": false,
  "timeout_seconds": 30,
  "env_dependencies": []
}
```

Пути в примере должны быть заменены конкретными проверенными путями. Структура не доказывает, что helper безопасен или операция разрешена.

Окружение дочернего процесса сохраняет совместимость с выбранным профилем исполнения; оно не становится герметичным. В binding включаются только зависимости, явно определённые доверенным профилем/анализатором, а не полный снимок окружения. Неподдерживаемая объявленная зависимость — отказ. Значения секретов не пишутся в spec/journal/identity; заявленное пустое множество от caller не доказывает отсутствие значимых зависимостей.

## Исполняемые файлы и интерпретаторы

- POSIX: нативный executable либо явно выбранный поддерживаемый интерпретатор и отдельный проверенный файл скрипта. Shell builtins без интерпретатора не поддерживаются.
- Windows: нативный `.exe`; прямые `.cmd/.bat` в первом структурированном пути отвергаются. `shell=false` сам по себе не исключает неявную оболочку Windows.
- Первый поддерживаемый сценарий скрипта — конкретный Python executable и отдельный файл; его зависимость фиксируется явно. Профиль должен различать допустимые флаги и inline-код.
- `bash -c`, `cmd /c`, PowerShell `-Command`, Python `-c/-m`, непрозрачные wrappers и неизвестные интерпретаторы не проходят как обычный безопасный structured workload. Первый MVP отказывает неподдерживаемому профилю; более широкая поддержка требует отдельного анализа.
- Прямой запуск не является песочницей. Нативная программа тоже может запускать shell или выполнять внешние действия; доверенный профиль и разрешение остаются необходимыми.
- Не вводить обязательный hash всех системных executable. Hash нужен для объявленных изменяемых script/artifact dependencies; revalidation executable определяется профилем. Подмена после последней проверки не исключается переносимым stdlib-кодом полностью.

## Вход в существующий CLI

Предлагаемые добавочные флаги `exec-risky`:

- `--verify-spec-file` — альтернатива строковым verify-аргументам;
- `--receipt-spec-file` — альтернатива строковым receipt-аргументам;
- `--rollback-plan-file` — альтернатива legacy rollback-команде и checkpoint-контракту;
- `--command-spec-file` — последующий этап #25A, взаимоисключающий с остатком командной строки после `--`.

Для каждой роли допускается один источник. Spec загружается, проверяется и удерживается в памяти до использования; файл не перечитывается молча после согласования. Все необходимые verify/receipt/rollback входы проверяются до основной mutation, а исполняемые зависимости повторно проверяются перед соответствующим запуском.

В ProcessSpec нет полей `approved`, `allow_critical`, policy decision или доверенных targets/effects. Существующие ручные подтверждения остаются внешними параметрами операции; `--approved` не становится доказательством разрешения в управляемой интеграции.

Строковый CLI остаётся совместимым и не переводится молча в новый строгий режим. Для него сохраняется существующая семантика; новые гарантии заявляются только для структурированного пути. Строка display может строиться для диагностики, но не используется для исполнения/identity. Текущий эвристический классификатор может сохранять консервативный отказ; structured input не расширяет SAFE/ALLOW.

## План отката #15

Отдельный `RollbackPlan v1` содержит: schema_version, exact target, program/cwd/timeout, зависимости, шаблон argv, собственный verify-spec и expected_state с непустыми assertions. Ни автоматический запуск, ни собственное разрешение в нём не допускаются.

Первый вариант зависимостей: только обычные файлы, без symlink/reparse в пути; до 32 файлов, до 8 МиБ каждый, до 32 МиБ суммарно. Каталоги, устройства, sockets, секреты и удалённые объекты отложены. Нужные права/метаданные целевого объекта описываются самим сценарием восстановления и его verify; копирование файла не обещает восстановление произвольных ACL/xattrs.

Для каждого файла: стабильный локальный ID, исходный путь, размер, SHA-256, путь сохранённой копии. Аргумент-ссылка задаётся отдельным объектом `{"artifact":"backup"}` и разворачивается целиком в один абсолютный путь копии. Подстрочная подстановка, `${...}`, glob и shell expansion запрещены. Остальные аргументы — буквальные строки. Развёрнутый результат — обычный ProcessSpec с массивом строк; самостоятельного исполнителя шаблонов нет.

Пример только списка аргументов плана:

```json
["-I", {"artifact":"restore_script"}, "--backup", {"artifact":"backup"}, "--target", "/approved/test/item"]
```

Сохранённый скрипт исполняется выбранным системным интерпретатором, не через executable-bit копии. Комплект хранится в `.agent-safety/recovery/<source-txn>/artifacts/`; manifest рядом. Директории контролируются текущим пользователем, ссылки/reparse запрещены. POSIX mode 0700/0600 применять к новым служебным объектам; на Windows не заявлять строгую ACL-изоляцию средствами одного chmod. Не использовать этот MVP для секретных артефактов.

### Подготовка до основного действия

1. Проверить весь план, точный target, типы файлов и лимиты до копирования.
2. Скопировать зависимости в новый каталог транзакции; сверить размер/hash копии и стабильность прочитанного источника. Изменение источника во время подготовки — отказ до основной mutation.
3. Зафиксировать manifest и план, сделать durable запись planned; если подготовка/journal не удались, основная команда не запускается. Частичные подготовительные артефакты не объявлять готовым rollback и не чистить автоматически.
4. Развёрнутые пути и семантически значимые зависимости должны быть известны до authorization binding. Если подготовка меняет смысл разрешённой операции, требуется повторная authorization, а не скрытая подстановка после неё.
5. Основное действие проходит существующие expected_state/verify/recovery правила. Для нового режима использовать незавершённый барьер до mutation, чтобы аварийный выход не разрешал продолжение.

Сохранение гарантирует воспроизводимость объявленных байтов, не полноту всех зависимостей произвольной программы. Если откат требует незафиксированный внешний ресурс, нужно явно описать и проверить его доступность либо отказаться от заявления о самодостаточности.

### Явное восстановление

Реализованный CLI: `safe recover --txn-id SOURCE --plan-file FILE --reason REASON --approved`.

- План должен совпадать с зафиксированным manifest/digest исходной транзакции. Изменившийся план требует отдельного пересмотра и нового согласования, а не тихого обновления.
- Восстановление получает новый txn ID и `parent_txn_id`. До запуска проверяются все зависимости, точные цели, доступность verify и binding самого восстановления.
- Разрешается ровно связанное восстановление при блокировке; нельзя добавлять публичный общий флаг обхода `INCIDENT_BLOCKED`. Несвязанная/нечитаемая блокировка или неопределённая связь — отказ и диагностика.
- Первоначальную блокировку/evidence сохранять. Последующие попытки восстановления требуют явного нового согласования; незавершённая предыдущая попытка не перезапускается автоматически.
- Результат проверяется собственными assertions. Даже успешный rollback не снимает исходный Recovery Mode автоматически; снятие — отдельное действие после проверки.
- Исторические строки `manual-command` не исполняются автоматически. `undo/redo` остаются файловыми операциями; их исправляет #26.

Журнал продолжает читать старые записи. Новые поля добавочны: metadata recovery mode, manifest digest, ссылка на исходную транзакцию, наблюдаемый исход. Исполняемые spec/артефакты остаются в локальном контролируемом комплекте; journal хранит только нужные ссылки/сведения. Это не объявляет весь старый journal очищенным для экспорта.

## Исходы процесса

| Наблюдение | Требуемая трактовка нового пути |
| --- | --- |
| Ошибка схемы/preflight | Не запущено; внешняя mutation отсутствует |
| Доказанная ошибка создания процесса | not_started; не подменять ею любое исключение |
| Получен процесс, затем timeout/прерывание/потеря результата | unknown, остановка и Recovery Mode; без retry |
| Ненулевой exit после запуска | Команда могла изменить состояние; unexpected |
| Exit=0, verify не подтвердил assertions | unexpected |
| Основное действие и verify успешны, receipt неуспешен | Частичный результат, Recovery Mode; не повторять mutation |
| Действие, verify и требуемый receipt успешны | done |

Текущий общий `_run` сводит обычные исключения к returncode=127; новое различение должно опираться на фазу запуска, а не на этот искусственный код. Тайм-аут завершения локального процесса не доказывает остановку всех потомков/удалённого действия. Не вводить неявное убийство дерева процессов.

Ограничение stdin не означает ограничение всей памяти захвата stdout/stderr. Существующее сохранение хвоста вывода также не является bounded capture. Не заявлять такой гарантии этим документом; переполнение/усечение verify не должно приниматься как полный JSON. Секреты и текст команд не включать в будущие ReliabilityEvent (#25C).

Для transport-required вызова без согласованной capability — явный отказ; существующий строковый SSH API остаётся. Выбор между upload + короткий exec и helper принадлежит исследованию ssh_relay#47; новый daemon/helper этим PR не устанавливается.

## Разбиение реализации и приёмка

1. После согласования — PR #15: внутренний ProcessSpec-потребитель для rollback/его verify, сохранение обычных файлов, явная recovery-транзакция. Не ждать публичного main-spec или событий #25C.
2. PR #25A: публичные verify/receipt/main spec входы и совместимость legacy. Основной исполнитель один; не дублировать recovery.
3. Отдельные #25B/#25C: JSON editor и событие. #16 использует готовые контракты после реального изучения Android-сценария.

Корпус проверок: пробелы/кавычки/пустой argv/Unicode/буквальный `$`/JSON argument; ошибочная схема до spawn; Windows executable/wrapper; потеря внешнего файла после сохранения; подмена сохранённого файла; превышение лимита; изменившаяся цель; сбой journal до/после mutation; timeout после запуска; verify/receipt failure; активный посторонний инцидент; старые записи; отсутствие слепого повтора. Для binding — drift argv/cwd/значимой env/script dependency без расширения ALLOW.

Обязательны штатные unittest, help, bootstrap dry-run и CI Windows/Ubuntu × Python 3.10/3.14. Ручной реальный SSH-прогон этим локальным MVP не заменяется.

## Принятое решение

Пользователь подтвердил рекомендованный вариант: локальный MVP через существующий exec-risky; строгие структурированные входы без `.cmd/.bat` и непрозрачных interpreter wrappers; ограниченный комплект обычных несекретных файлов; отдельное явное восстановление с собственным verify и сохранением блокировки; удалённую structured-схему отложить до совместного решения #34/#47. Слияние PR и изменения реальных серверов этим решением не разрешены.

## Границы первой реализации #15

Первый проверяемый профиль: одна обычная файловая цель до 8 МиБ (или отсутствующий файл), текущий канонический Python с `-I` и сохранённым скриптом для отката и проверки. Другие программы, каталоги как цель и зависимости окружения откладываются до отдельных профилей. Артефакты требуют явное `non_secret: true`; это заявление автора, не автоматическое доказательство. Публичные структурированные входы основного действия/verify/receipt остаются #25A.

Восстановление дополнительно проверяет наблюдаемое состояние цели после исходного действия; внешнее изменение требует отдельного разбора. Исключительный ACTIVE-барьер предотвращает одновременные попытки. Завершённую неуспешную попытку можно повторить только с отдельным согласованием и ссылкой `--retry-after`; неизвестный исход и незавершённая запись требуют ручного разбора.
