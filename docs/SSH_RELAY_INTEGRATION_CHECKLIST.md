# Ограниченная интеграционная проверка SSH-адаптера

Статус: подготовленный сценарий, **не выполнен**, 19.09.2026. Продолжает #4 через [#27](https://github.com/dilukhin/agent-safe/issues/27). Перед реальным запуском требуется исправление проверки endpoint из #27.

## Допуск к прогону

Исполнитель заполняет таблицу после read-only discovery и согласования конкретного окружения. Значения не заимствуются из чужого проекта или старого диалога.

| Параметр | Сессия A | Сессия B |
| --- | --- | --- |
| Имя relay-сессии | Не назначено | Не назначено |
| Подтверждённые host / port / user | Не назначены | Не назначены |
| Подтверждение SSH host identity | Не получено | Не получено |
| Пользовательский временный каталог | Не назначен | Не назначен |
| Точный root-owned тестовый каталог | Не назначен | Не назначен |
| Системный receipt path и доверенный родитель | Не назначены | Не назначены |
| Тестовая цель, исходные bytes/права, expected state | Не зафиксированы | Не зафиксированы |
| Способ и проверка восстановления | Не согласованы | Не согласованы |

Зафиксировать exact source/build SHA agent-safe и ssh_relay, клиентскую ОС/Python и сведения ОС целей без секретов. Проверить совместимость машинного контракта и доступность exec/sudo-exec. Сессии должны разрешаться в выбранные endpoint; один host_label этого не доказывает. Не читать session tokens/пароли и не выводить настройки, содержащие их.

Изменения ограничить заранее созданными тестовыми объектами. Подготовка тестового каталога, root-owned файла и receipt location тоже меняет состояние: назначить владельца, exact paths, разрешение и восстановление до подготовки. Не менять system services, пакеты, firewall, облачные VM или рабочие данные ради этого прогона.

## Порядок

1. Подтвердить identity обеих сессий read-only запросами; сохранить очищенный результат и исходное состояние тестовых целей. Не заменять неизвестные команды пробным запуском с `--help`, если скрипт может выполнить действие до разбора аргументов.
2. A / exec: одно минимальное изменение пользовательского тестового файла через safe ssh-relay-risky. Использовать уникальное безопасное содержимое-маркер; expected assertions — exact target, marker/hash и нужные права. До запуска записать восстановление исходного состояния.
3. Убедиться: main и verify совпадают по session/host/port/user/mode; verify не меняет состояние; txn ID связан с remote receipt ID/hash; текущая тестовая цель совпадает с assertions. Сверку remote receipt выполнять read-only на разрешённом пути.
4. Выполнить отдельное явно согласованное восстановление тестового состояния, записать его evidence и verify. Сам факт передачи rollback-command в исходную операцию не означает его исполнения.
5. Повторить B / exec с другим marker и другим exact target. Проверить, что цель и подтверждение A не изменены и не использованы как результат B.
6. A / sudo-exec: одно изменение заранее согласованного root-owned тестового файла, verify тем же sudo-режимом, отдельный системный receipt path. Затем явное восстановление с проверкой владельца/прав/bytes.
7. Повторить B / sudo-exec; проверить раздельность исходных транзакций, целей и receipt ID. Успех launcher не считать результатом операции.
8. Проверить локальный journal и разрешённые remote receipts на отсутствие тестовых чувствительных маркеров; реальные секреты в качестве тестовых данных не использовать. Hash команды не заменяет содержательную проверку фактического состояния.
9. Подтвердить конечное восстановленное состояние всех четырёх сценариев. Очистка временных объектов — отдельное согласованное действие после принятия evidence; самопроизвольной очистки при сбое нет.

## Отказы и остановка

Неверный endpoint, отсутствие/несовпадение receipt, partial_success, unknown, timeout, неуспешный verify или неожиданное состояние: остановить исходный прогон, сохранить evidence, только read-only диагностика. Не повторять исходную mutation и не снимать блокировку ради продолжения следующего пункта.

Проверки неправильного endpoint, некорректного JSON, сбоя receipt и неизвестного результата в первую очередь выполняются имитационными тестами. Преднамеренный disconnect/изменение alias/лишение прав на живой цели — отдельный сценарий с собственной оценкой риска; в этот прогон по умолчанию не входит.

Восстановление после фактического неожиданного результата требует пересмотра плана на основе evidence. Заранее описанный rollback не является разрешением импровизировать после инцидента.

## Отчёт и критерий завершения

Для каждого из A/exec, B/exec, A/sudo-exec, B/sudo-exec: exact revisions, согласованный target, очищенные endpoint identity, txn/receipt ID/hash, expected и actual state, исход verify, отдельная запись восстановления и итоговое состояние. Не включать командные payload, пароли, ключи, tokens или лишние частные пути.

Прогон завершён только когда все четыре случая подтверждены, состояния восстановлены и нет необъяснённого смешения целей/receipts. Если отдельный случай не выполнялся, статус — частично, а не success. Исправление unit-теста endpoint не заменяет этот отчёт.
